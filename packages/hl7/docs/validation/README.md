# Validation records

How the HL7 facts in `@campfhir/hl7` were checked, and against what.

- [`v2.3-segment-ledger.md`](v2.3-segment-ledger.md), [`v2.3.1-segment-ledger.md`](v2.3.1-segment-ledger.md),
  [`v2.4-segment-ledger.md`](v2.4-segment-ledger.md) and [`v2.5-segment-ledger.md`](v2.5-segment-ledger.md):
  every field of every segment of the
  version compared with hl7.eu, the Caristix reference and HAPI, with the date the sources were
  read, the value decided for each attribute, every contradiction between the sources, what our
  class implements (its own class, a generated subclass of an older class, an older version's class
  re-exported, or none yet for a segment new in the version), and which tests cover it. Generated
  by `codegen/validate/ledger.mjs <version>`; hand-written decisions are in
  `codegen/validate/ledger-v23-notes.json`, `ledger-v231-notes.json`, `ledger-v24-notes.json` and
  `ledger-v25-notes.json`.
- [`v2.3-message-ledger.md`](v2.3-message-ledger.md), [`v2.3.1-message-ledger.md`](v2.3.1-message-ledger.md),
  [`v2.4-message-ledger.md`](v2.4-message-ledger.md) and [`v2.5-message-ledger.md`](v2.5-message-ledger.md):
  every message structure of the version
  rendered in the standard's abstract syntax from our schema, the hl7.eu chapter tables (v2.3,
  v2.4 and v2.5; hl7.eu publishes no 2.3.1 chapters), Caristix and HAPI, compared by shape, with the
  deliberate modelling decisions and their reasons dated in `codegen/validate/message-notes.json`,
  and the version's events we do not implement yet, if any. Generated by
  `codegen/validate/message-ledger.ts <version>`. A new version's missing events are drafted from
  the Caristix tables by `codegen/validate/scaffold-messages.ts` and then checked by the ledger.
- [`v2.3-hl7eu-sweep.md`](v2.3-hl7eu-sweep.md) and
  [`v2.3-hapi-crosscheck.md`](v2.3-hapi-crosscheck.md): the first sweeps (2026-10-19), superseded
  by the ledger and kept for the history of the decisions.

## The rule

hl7.eu is the authoritative source for a segment's field table. When the sources disagree on a
field's type, repeat, usage or length, hl7.eu's value is used unless Caristix and HAPI agree with
each other against it; then the two of them win. Whichever way it goes, the disagreement is written
in the field's row of the ledger with the value each source gave, so nobody has to look it up
again. When hl7.eu contradicts itself (its segment index page against the printed chapter text,
as for NSC), the printed text wins and the decision is recorded in the notes file with its date.

## Refreshing the ledgers

```sh
codegen/validate/fetch-sources.sh v2.4 /tmp/hl7-sources/v2.4   # hl7.eu pages, Caristix JSON, HAPI classes of our segments
node codegen/validate/ledger.mjs v2.4 /tmp/hl7-sources/v2.4     # writes v2.4-segment-ledger.md
node codegen/validate/ledger.mjs v2.4 /tmp/hl7-sources/v2.4 --fix-spec   # also corrects codegen/spec/v2.4-segments.json
node codegen/validate/ledger.mjs v2.4 /tmp/hl7-sources/v2.4 --adopt OM1,PID,SAC   # seeds the version's spec for segments that get their own class
```

`fetch-sources.sh` fetches the segments that have a module in the version; a segment new in the
version is added by downloading its three files into the same directories (its Caristix segment list,
`https://hl7-definition.caristix.com/v2-api/1/HL7v2.4/Segments`, names them all), after which the
ledger lists it as "none yet" and `--adopt` seeds its table from the sources. `--adopt` of a
hand-written class writes a subclass entry (`"extends"`, with the fields the base already implements
marked `inherited`), which `generate-segments.ts` turns into a subclass with setters for the new and
changed fields only.

The message ledger reads the Caristix trigger-event JSON, HAPI's message and group classes with its
event map, and (for v2.3) the hl7.eu chapter pages:

```sh
npx tsx codegen/validate/message-ledger.ts v2.3 --caristix /tmp/caristix/v2.3 --hapi /tmp/hapi23/message /tmp/hapi23/group /tmp/hapi23/2.3.properties --hl7eu /tmp/hl7eu-v23
npx tsx codegen/validate/message-ledger.ts v2.3.1 --caristix /tmp/caristix/v2.3.1 --hapi /tmp/hapi231/message /tmp/hapi231/group /tmp/hapi231/2.3.1.properties
npx tsx codegen/validate/message-ledger.ts v2.4 --caristix /tmp/caristix/v2.4 --hapi /tmp/hapi24/message /tmp/hapi24/group /tmp/hapi24/2.4.properties --hl7eu /tmp/hl7eu-v24
npx tsx codegen/validate/message-ledger.ts v2.5 --caristix /tmp/caristix/v2.5 --hapi /tmp/hapi25/message /tmp/hapi25/group /tmp/hapi25/2.5.properties --hl7eu /tmp/hl7eu-v25
npx tsx codegen/validate/scaffold-messages.ts v2.5 --caristix /tmp/caristix/v2.5 --events OML_O33,ORL_O34 --out codegen/schemas/v2.5/draft.ts
```

The Caristix directory holds one `<EVENT>.json` per trigger event of the version
(`https://hl7-definition.caristix.com/v2-api/1/HL7v2.4/TriggerEvents` lists them); the HAPI
directories are `hapi-structures-v24/src/main/java/ca/uhn/hl7v2/model/v24/message` and `group` of a
checkout with the event map from `src/main/resources/ca/uhn/hl7v2/parser/eventmap`; the hl7.eu
directory holds the chapter pages `https://www.hl7.eu/HL7v2x/v24/std24/ch02.htm` … `ch15.htm`
(`std23/ch2.htm` … for v2.3; `std25/ch02.html` … `ch15.html` for v2.5, saved under `.htm` names so
the reader picks them up). The v2.5 pages print each table row with the segment in its first cell
and a description in the second; the reader keeps those two cells only, reads an `OBR` row
described as the "Order Detail Segment" (followed or not by the `RQD` … `ODT` rows) as the order
detail choice, and the HAPI event map names the events that share a class (`hapi-structures-v25/
src/main/resources/ca/uhn/hl7v2/parser/eventmap/2.5.properties`).

After `--fix-spec`, regenerate the generated classes (delete them and run
`npx tsx codegen/generate-segments.ts --version v2.4`, then `pnpm test:positions`) and run the
ledger again. A version whose segment re-exports an older class is checked against that class; when
the version's table differs, `--adopt` copies the table into the version's spec with the decided
values, the re-export stub is deleted and the class generated (a hand-written base class gets a
generated subclass, as `src/segments/v2.4/PID.ts`, or a hand-written one, as
`src/segments/v2.3.1/RXA.ts`).
