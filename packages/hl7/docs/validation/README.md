## The rule

hl7.eu is the authoritative source for a segment's field table. When the sources disagree on a
field's type, repeat, usage or length, hl7.eu's value is used unless Caristix and HAPI agree with
each other against it; then the two of them win. Whichever way it goes, the disagreement is written
in the field's row of the ledger with the value each source gave, so nobody has to look it up
again. When hl7.eu contradicts itself (its segment index page against the printed chapter text,
as for NSC), the printed text wins and the decision is recorded in the notes file with its date.

## Refreshing the ledgers

Every source is pulled by `codegen/validate/fetch-sources.sh`, which uses curl, git and jq and chooses
nothing by hand: the segment list comes from the hl7.eu segment index of the version, the event list
from Caristix's TriggerEvents index, and HAPI is a sparse clone whose commit is recorded. Each fetch
is one line of `MANIFEST.tsv` in the target folder (source, URL, status, bytes, SHA-256), and
`--record` copies that manifest to `codegen/validate/sources/<version>.tsv`, so the commit that
changes a ledger also shows the sources it was built from.

```sh
codegen/validate/fetch-sources.sh v2.5.1 ~/hl7-sources/v2.5.1 --record   # hl7.eu, Caristix and HAPI into one folder
npx tsx codegen/validate/message-ledger.ts v2.5.1 --caristix ~/hl7-sources/v2.5.1/caristix/events --hapi ~/hl7-sources/v2.5.1/hapi/message ~/hl7-sources/v2.5.1/hapi/group ~/hl7-sources/v2.5.1/hapi/eventmap.properties --hl7eu ~/hl7-sources/v2.5.1/hl7eu/chapters
node codegen/validate/ledger.mjs v2.5.1 ~/hl7-sources/v2.5.1     # writes v2.5.1-segment-ledger.md
node codegen/validate/ledger.mjs v2.5.1 ~/hl7-sources/v2.5.1 --fix-spec   # also corrects codegen/spec/v2.5.1-segments.json
node codegen/validate/ledger.mjs v2.5.1 ~/hl7-sources/v2.5.1 --adopt OM1,PID,SAC   # seeds the version's spec for segments that get their own class
```

The script exits with status 1 when a source fails (a server error after retries); a page the source
does not have is recorded as `absent`, which is not a failure. Because the hl7.eu index names every
segment of the version, a segment new in the version is fetched like the others, and the ledger lists
it as "none yet" until `--adopt` seeds its table from the sources. `--adopt` of a
hand-written class writes a subclass entry (`"extends"`, with the fields the base already implements
marked `inherited`), which `generate-segments.ts` turns into a subclass with setters for the new and
changed fields only.

The message ledger reads the Caristix trigger-event JSON, HAPI's message and group classes with its
event map, and the hl7.eu chapter pages, all of them from the folder `fetch-sources.sh` writes. The
scaffold for a version's missing events reads the same Caristix events:

```sh
npx tsx codegen/validate/scaffold-messages.ts v2.5 --caristix ~/hl7-sources/v2.5/caristix/events --events OML_O33,ORL_O34 --out codegen/schemas/v2.5/draft.ts
```

The Caristix events are `caristix/events/<EVENT>.json`, one per message in the TriggerEvents index
(`https://hl7-definition.caristix.com/v2-api/1/HL7v2.5.1/TriggerEvents`). The HAPI folder is the
`message` and `group` classes of `hapi-structures-v<n>` and its event map, copied from the sparse
clone of `hapi-hl7v2` at the commit recorded in the manifest. The hl7.eu chapter pages are named in
the version's segment index (`ch02.html` …, in `std<n>/`) and saved as `hl7eu/chapters/chNN.htm`. The v2.5 pages print each table row with the segment in its first cell
and a description in the second; the reader keeps those two cells only, reads an `OBR` row
described as the "Order Detail Segment" (followed or not by the `RQD` … `ODT` rows) as the order
detail choice, and the HAPI event map names the events that share a class (`hapi-structures-v25/
src/main/resources/ca/uhn/hl7v2/parser/eventmap/2.5.properties`).

After `--fix-spec`, regenerate the generated classes (delete them and run
`npx tsx codegen/generate-segments.ts --version v2.4`, then `pnpm test:positions`) and run the
ledger again. A version whose segment re-exports an older class is checked against that class; when
the version's table differs, `--adopt` copies the table into the version's spec with the decided
values, the re-export stub is deleted and the class generated (a hand-written base class gets a
generated subclass, as `src/segments/v2.4/PID.ts`, or a hand-written one, as
`src/segments/v2.3.1/RXA.ts`).
