# Roadmap: Segments

Tracks which HL7 v2 segments have a hand-written class in `src/segments/<version>/`.
The goal is **complete HL7 v2.3 coverage first**, then v2.5.1 parity, then later versions
(see [ROADMAP.md](../ROADMAP.md)).

## Source of truth

The v2.3 segment list below comes from the HL7 v2.3 segment index on hl7.eu
(`https://www.hl7.eu/HL7v2x/v23/hl7v23segm.htm`, read 2026-10-19). Field tables come from the
per-segment pages on hl7.eu, e.g. `https://www.hl7.eu/HL7v2x/v23/hl7v23segmQRD.htm`, with the
Caristix tables (`https://hl7-definition.caristix.com/v2`) as the validation reference.

Where a field table on hl7.eu gives no usage or repeat value, the field is implemented
without a required flag and the gap is noted here. Those notes are unverified and should be
confirmed before anything depends on them.

Each segment needs: class with fluent setters + `encode()`, a parser, a co-located
`<SEG>.test.ts` (including field-position tests), and an entry in the barrel (`pnpm barrels`).
Segments that hand-write their field-position tests carry the `position-tests: hand-written`
marker, so `pnpm test:positions` skips them.

Segments are placed in the version that introduced them: `PDA`, `ABS`, `BLC`, `RMI` and the staff
master file segments `ORG`, `AFF`, `LAN`, `EDU` and `OM7` are in `segments/v2.4`, and `SFT`, `SPM`, `TQ1`,
`TQ2`, `CER` and `IIM` are in `segments/v2.5` (with a v2.5 `EDU` subclass for the EDU-9 added in 2.5);
later versions re-export them. `ROL` and `DB1` both have v2.3 definitions, so
they stay in `segments/v2.3`. (Version-specific fields are layered, not moved: `ROL` fields 9–12, `ACC` fields 7–10 and `PD1` fields 13–21 are v2.4 overrides in `segments/v2.4`; `ACC` field 11 is a v2.5 override. The v2.3 classes stop at the v2.3 field count. `DB1` has the same eight fields in v2.3, v2.4 and v2.5. Field 3 (CX) repeats in all three, and v2.3 now models that. v2.4 widens its maximum length to 250, which is not enforced, and hl7.eu names field 4 "Disability Indicator" in v2.4 and "Disabled Indicator" in v2.3 and v2.5.) Moving a
segment is `git mv` into the introducing version directory, adding it to that version's
`ownSegments` in `codegen/schemas/`, and running `pnpm codegen && pnpm barrels`.

### Unverified details in built segments

(Kept from the first sweep; the ledger above is the current state of every field.)

- `AIP-4` is named "Resource Role" in the Caristix table; the setter is still `resourceType()` for API compatibility.
- `AL1-2` is named "Allergy Type" in the Caristix table; the setter is `allergenTypeCode()`.
- `QRD-11` (What Data Code Value Qualifier) is typed `CM_VR` on hl7.eu. It is written as
  repeating single components until the CM composite layout is modelled.
- `QRF-9` (When Quantity/Timing Qualifier) is typed `TQ`. It takes positional components and
  does not yet name them.
- `QRD` and `QRF` usage flags are not stated on hl7.eu for several fields.

## v2.3 coverage

All 110 segments of the v2.3 segment index now have a class. The 60 segments that were already
hand-written are in the built list above. The other 50 were generated by
`codegen/generate-segments.ts` from `codegen/spec/v2.3-segments.json`, the field tables transcribed
from the Caristix reference (the same generator produces later versions' segments from
`codegen/spec/<version>-segments.json`, e.g. `--version v2.4` for ORG, AFF, LAN, EDU, OM7 and
`--version v2.5` for CER, IIM, validated against the Caristix and hl7.eu tables of that version):

APR, ARQ, AUT, CDM, CM0, CM1, CM2, CSP, CSR, CSS, EQL, ERQ, FAC, GOL, LCC, LCH, LDP, LOC, LRL, MFA, NCK, NPU, NSC, NST, OM1, OM2, OM3, OM4, OM5, OM6, PCR, PDC, PEO, PES, PRB, PRC, PRD, PSH, PTH, RDF, RDT, RF1, RXC, RXG, SPR, TXA, URD, URS, VAR, VTQ

Generated classes are correct on field positions, repetition and the composite datatypes that have a
typed object in `utils/composites.ts` (CE, CX, XCN, XPN, XAD, XTN, EI, PI, PL, CP, PLN, LA2, XON, CWE);
their other setters take raw HL7 values. `src/segments/v2.3/generated.test.ts` checks every
generated setter, repetition and composite against the spec, and `roundtrip.test.ts` parses and
re-encodes every one of the 110 classes. Replace a generated file with a hand-written class and the
generator will leave it alone.

## Validation ledger (v2.3)

Every field of every v2.3 segment is compared with three sources in
[`docs/validation/v2.3-segment-ledger.md`](validation/v2.3-segment-ledger.md): the hl7.eu segment
pages (authoritative), the Caristix tables (validation reference) and HAPI's v2.3 field definitions
(cross-check). hl7.eu decides a disputed type, repeat, usage or length unless Caristix and HAPI
agree with each other against it; every disagreement is written in the field's row either way, with
the date the sources were read. Hand-written decisions (a count or value that overrides the rule,
or a deliberate divergence) live in `codegen/validate/ledger-v23-notes.json` with their date and
reason. To refresh: `codegen/validate/fetch-v23-sources.sh <dir>` then
`node codegen/validate/ledger-v23.mjs <dir>` (add `--fix-spec` to write the decided values into
`codegen/spec/v2.3-segments.json`, then regenerate the classes). The ledger also records, per
segment, which tests exist (position tests, hand-written tests, round trip, spec-driven) and which
setters only the position tests call.

Sweep of 2026-10-25: the spec of the generated classes was corrected on 40 values (lengths and
usages Caristix had differently from hl7.eu and HAPI, NSC-1's type, OM1-6's type); AIP-5 now takes
repetitions; parsed fields now expose their repetitions (`Field.repetitions`), which the parser used
to leave joined inside the first component; and MSH/BHS/FHS now encode repeating fields (they used
to drop everything after the first repetition). The earlier reports in `docs/validation/` are kept
for their history; the ledger supersedes them.

## v2.5.1 parity
v2.5.1 segments are generated as thin wrappers over the v2.3 base (`pnpm codegen`), so every
v2.3 segment above must also be re-evaluated for v2.5.1 field changes. After v2.3 is complete,
add the segments introduced after 2.3, e.g. `TQ2`, `PRT`, `QPD`, `RCP`, `QID`, `IAM`,
`GP1`/`GP2`, `OH1`–`OH4`, `CNS` (verify against the 2.5.1 spec). Segments on the v2.3 index above
(`ARQ`, `APR`, `CSP`) stay in the v2.3 plan.

## Definition of done (per segment)
1. Class + parser with all fields positioned per spec, including repeats and required flags.
2. Field-position tests (hand-written with the marker, or generated with `pnpm test:positions`).
3. Round-trip test (encode → parse → encode).
4. Barrel regenerated (`pnpm barrels`), `pnpm lint && pnpm typecheck && pnpm test` green.
